# 待办的多阶段时间设计

日期：2026-10-10。本文记录个人待办多阶段时间的设计与本次实施范围。

建议保留普通待办的截止时间，并让一个事项按需拥有多个自定义时间阶段。准备、提交、审核、执行、验收、预约等使用同一套阶段模型。每个阶段分别记录时间、完成情况和提醒，事项保持一个标题、一个入口和一个总体完成状态。界面的主要入口使用“添加阶段”，阶段名称由用户填写，预约属于可选示例。

先满足用户的三个动作：快速记下一件事、补充它的时间安排、每天知道下一步做什么。普通待办维持“内容 + 可选时间”的录入成本；第一层直接支持截止时间和单段起止时间。只有需要多段安排时，界面才展开阶段名称与管理能力。

### 用户体验的主要取舍

1. 录入从简单开始。时间范围、多个阶段、提醒细节逐步展开；复杂事项的编辑界面主动展示已填写阶段，避免藏起重要日期。
2. 单段安排直接填时间，无需先命名阶段。增加第二段时再展示阶段名称，使用可修改的初始名称；名称暂时没想好也可以先保存。准备、报名、测试、交付等均使用同一个入口。
3. 阶段内容与日程占用分别表达。收起的设置用“可在期间完成”“需要按时参加或执行”“只跟踪时间，等待后续”表达用途，并映射完成要求与占用检查。用户无需分别理解两个布尔开关。
4. 列表突出下一步。阶段名称、当前提示、关键日期和阶段完成动作常驻；完整时间线通过“查看全部阶段”展开。
5. 操作保留余地。阶段完成、删除和改期可以撤销；填写一半、具体时刻未知、结束待定都能保存。只校验用户确实填写的信息。
6. 先保证默认值可理解。提醒显示“开始时提醒”“结束前一天提醒”等自然语言；用户可以修改或关闭，系统不根据阶段名称擅自改变提醒或完成状态。

布局采用按需展开：录入时一次编辑一段安排，每天查看时突出当前行动，完整时间线通过“查看全部安排”展开。编辑表单与时间线共享同一份阶段数据。

## 1. 时间表达

需要区分三种含义，它们可以组合使用。

| 时间含义 | 例子 | 应产生的行为 |
| --- | --- | --- |
| 截止时间 | 10 月 12 日 18:00 前交作业 | 到期前提醒，未完成则标记逾期 |
| 可处理时段 | 10 月 10 日 09:00 至 12 日 18:00 准备材料，或在此期间报名 | 开始前、结束前可分别提醒，支持标记阶段完成 |
| 固定安排 | 10 月 15 日 14:00 至 16:00 执行任务或参加活动 | 开始前提醒，展示即将开始、进行中、已结束，可参与日程冲突检查 |

这些日期均为虚构示例。“固定安排”表示计划发生的时间；用户实际投入的时间继续由现有专注记录和实际用时表达。只记录审核、物流等外部进度的阶段，可以关闭“需要标记完成”和日程占用，保留时间和通知。

普通作业可以只填截止时间；会议可以只填正式安排；报名参加考试可以同时填报名时段和考试安排；需要提交材料的活动可以再增加一个材料提交时段。阶段名称由用户修改。

阶段支持独立的开始日期和结束日期，每个日期的具体时刻均可留空。只知道一个端点时保存已知信息，另一端显示“待定”。只有一个已知时间点也可以记录，提醒绑定那个端点。全部日期待定的阶段保留在事项中，供以后补充。

## 2. 编辑界面

普通待办继续提供现有截止日期、截止时间和快捷日期；基础时间同时提供“起止时间”入口，单段安排直接编辑时间，无需命名。已有截止时间保留在可选的事项截止区域，用户自行确定是否同时使用。需要更多安排时点击“添加阶段”，此时再出现阶段名称。新阶段使用可修改的初始名称，保存时名称留空则补为“阶段 N”，日期可以全部待定。

每个阶段显示：

- 名称：准备、提交、审核、执行等，可直接输入和修改。
- 开始日期；需要精确到小时再添加时刻，已有时刻直接展示。结束待定时通过“添加结束时间”补充，可恢复为结束待定。
- 一行提醒摘要；点击设置后再修改开始、结束提醒的开关和提前量。
- 收起设置中的安排方式：可在期间完成、固定参加或执行、只跟踪时间；同时包含开始和结束提醒。设置摘要直接说明当前安排方式与提醒。
- 对需要完成的阶段提供“完成此阶段”，并支持撤销；相应按钮可使用“已提交”“已预约”等用户设置的自然动作名称。

默认只展示事项已经使用的阶段；编辑时一次展开一个阶段，其他阶段展示名称、时间和提醒摘要。阶段可以删除或调整显示顺序；显示顺序表达用户的安排顺序，时间排序由实际日期计算。排序同时提供上下移动按钮，支持手机和键盘。删除保留撤销能力。后续模板只在用户主动选择时填入，不根据标题自动改变现有字段。

手机端每个阶段使用一张纵向卡片，开始与结束日期分行展示。填写报错定位到具体阶段、具体端点，保存失败时保留输入。

## 3. 时间状态与完成状态

系统按当前时间计算阶段的时间状态；用户操作记录完成状态。两者分别保存和展示。

| 情况 | 显示 | 后续处理 |
| --- | --- | --- |
| 预约尚未开放 | 预约将于 10 月 10 日 09:00 开放 | 保留开放提醒 |
| 预约窗口已开放，尚未确认办理 | 预约开放中，10 月 12 日 18:00 关闭 | 提供已办理按钮，保留关闭前提醒 |
| 用户标记已预约 | 已预约 · 等待正式开始 | 取消该阶段的后续办理提醒，保留正式安排提醒 |
| 预约窗口关闭，尚未确认办理 | 预约窗口已关闭 · 待确认 | 展示风险提示，允许补记已办理或取消事项 |
| 正式时间正在进行 | 活动进行中，16:00 结束 | 保持事项的人工完成状态 |
| 正式时间已结束，事项尚未完成 | 活动已结束 · 待确认完成 | 保留记录，允许完成、取消或改期 |
| 事项被标记完成、取消或归档 | 相应总体状态 | 停止此事项的所有阶段提醒 |

窗口关闭后，系统无法知道用户是否已在其他地方成功预约，所以显示“待确认”；只有用户明确确认失败时才使用“已错过”等结论。

窗口开放不自动把看板中的事项移到“进行中”。正式安排经过结束时间也不自动勾选完成。前一阶段完成只改变该阶段。列表主要按钮优先处理当前阶段；确认没有其他未完成或尚未结束的安排时，最后一步可以明确显示“完成事项”，在同一次用户操作中完成该阶段和总事项。

“直接完成整个事项”放在更多操作里。还有未完成阶段、等待中的外部进度或未来安排时，先在事项下方说明剩余数量，再让用户确认完成整体；阶段原有完成事实保留。确认界面可返回继续处理阶段。撤销整体完成时恢复操作前的完整状态。

没有结束时间的正式安排，在开始后显示“已开始 · 结束时间待定”。不使用预计时长推断真实结束时间。通用阶段使用“待开始”“可处理”“时间范围已结束 · 待确认”等提示；预约模板可以使用“待开放”“开放中”“已关闭”等贴合语义的文案。

事项明确设置的截止时间继续独立判断逾期。预约关闭、活动结束显示各自的阶段提示；用户完成预约后，该阶段的关闭提示从当前风险中移除。总体截止时间由用户明确设置。

## 4. 列表、首页与日历

列表一条事项保持一行，突出当前需要处理的阶段，例如“预约开放中 · 周日 18:00 关闭”；已办理后显示“已预约 · 周四 14:00 开始”。展开详情才能看到完整时间安排。当前风险可以与下一个正式安排同时显示。

“已安排”按是否存在有效截止时间或有效阶段日期判断。所有日期均待定时归入“待安排日期”。搜索和日期范围筛选覆盖阶段名称及端点日期，避免只有正式时间的事项被隐藏。

排序选项增加“按下一步时间”，作为多阶段事项的默认时间排序。办理窗口尚未开放时使用开放时间；开放期间使用关闭时间；已办理后使用下一段正式时间。已有截止时间也参与下一步候选。已关闭且待确认的窗口进入风险区，其他未来阶段继续可见。仅有截止时间的旧待办维持原排序结果。

月历和周视图按阶段显示“预约开放”“预约截止”“活动安排”等标记；跨日正式安排覆盖对应日期。预约窗口用开始、结束标记和轻量区间表达，避免把每一天都列成一条待办。点击任意标记打开同一事项，并定位到该阶段。统计待办数量时按事项 ID 去重，日历标记数量单独统计。

已有日程页可以展示正式安排的派生条目。阶段数据保存在事项中，日程页读取同一份数据；修改派生条目回到原事项的编辑入口。页面间共享事项和阶段标识，提醒也使用同一个调度入口。

## 5. 提醒规则

- 可办理时段支持开放前、关闭前提醒；正式安排默认提醒开始，结束提醒由用户按需开启。
- 每个提醒明确绑定一个阶段的开始或结束。提醒文字包含阶段名称和动作，例如“预约将在 30 分钟后关闭”。
- 同一阶段可以有多个提前量，零分钟仍表示到点提醒；关闭提醒使用单独的开关。
- 预约已办理后停止该阶段未来提醒；撤销已办理重新计算尚未触发的提醒。
- 去重标识包含事项、阶段、提醒 ID，触发签名包含目标时间和提前量。改标题保留去重，改时间按新目标排程。
- 同一事项、同一触发时刻的提醒合并展示，并保留各阶段说明。
- 补响应检查阶段是否仍可操作。窗口已关闭时，不再补发“即将开放”或“即将关闭”的过时通知，关闭且待确认的信息由风险区展示。

精确到时刻的安排使用应用现有时区设置。只有日期时，界面明确显示“时间待定”，日期粒度的窗口开始按当天开始、窗口结束包含结束日全天；日期提醒提供可见的提醒时刻，例如当天 09:00。旧截止时间的日期与提醒口径保持兼容，历史提醒继续按原来的 23:59 规则计算。

提醒能力沿用当前应用的通知调度方式；本设计不包含新增服务端推送。

## 6. 校验与冲突

开始和结束都已知时，结束须晚于开始；允许同一天的纯日期范围，因其包含当天。跨日安排通过独立结束日期表达，例如 10 月 15 日 23:00 至 16 日 01:00。只有日期时保留日期精度，避免界面暗示用户已经确定具体小时。

跨阶段的时间关系默认允许自由组合。预约可以持续到活动进行期间，材料提交也可能在活动之后。模板可以在可疑顺序时提示检查，用户可以继续保存。

预约、报名等办理窗口表示可选时段。只有明确占用时间的正式安排参与时段冲突检查；开始或结束的具体时刻缺失时，提示时间信息不完整。相邻安排的首尾相接不算重叠，跨日重叠按完整日期时间计算。明确选择全天安排时再按全天占用检查。

截止时间参与到期提醒；明确的正式安排参与占用检查。预计时长继续用于工作规划。

## 7. 数据模型与模块接口

保留现有 `Task.dueDate`、`dueTime`、`done`、`status`、`reminderMinutes`，按需增加 `timeStages`。缺失阶段数组等同空数组。每个阶段建议包含：

```ts
type StageBoundary = { date: string; time?: string }

type TaskTimeStage = {
  id: string
  label: string
  kind: 'window' | 'scheduled'
  start?: StageBoundary
  end?: StageBoundary
  allDay?: boolean
  completionRequired?: boolean
  completedAt?: string | null
  reminders?: Array<{
    id: string
    anchor: 'start' | 'end'
    minutesBefore: number
    enabled: boolean
    dateOnlyTime?: string
  }>
}
```

`window` 表示可自行处理的时间范围，`scheduled` 表示占用日程的固定安排；界面通过“占用我的日程”设置映射此差异。单个端点提供时间点表达。`allDay` 是用户明确选择的全天安排。`completionRequired` 决定阶段是否需要人工确认完成，关闭时结束后仅显示已结束。阶段 ID 和提醒 ID 在编辑、排序与同步中保持稳定。时间状态随时钟派生，持久化仅记录用户设置和完成事实。

日期字段允许部分填写；边界的具体时刻依赖有效日期。没有目标端点的提醒保持未启用，界面引导补充日期。日期精度、跨日、时区转换与格式化收在时间模块内部。

增加一个负责阶段时间的深模块，Interface 围绕三项能力：校验输入、派生当前时间摘要、生成时间条目。时间条目携带事项 ID、阶段 ID、端点角色和时间精度，由列表、首页、日历、通知及冲突检查分别消费。调用方无需自行推断哪个字段是预约时间，也无需各自计算窗口状态。

写入命令复用相同校验，覆盖手动编辑、快速记录、导入和改期。阶段完成命令只更新目标阶段；整体完成继续走现有事项命令。暂不引入阶段依赖图或独立工作流引擎。

## 9. 兼容、改期与重复

旧待办无需补齐四个日期，读取为“一个截止时间、零个阶段”。已有截止日、完成记录、重复规则和提醒记录保持可读。阶段数据跟随现有事项集合保存，备份与恢复必须验证往返一致性。

改期提供单段编辑和“移动剩余安排”。用户选择提前或顺延，并组合填写天、小时和分钟，例如 2 小时、1 天 2 小时、2 天 3 小时 30 分钟。先按日历日移动，再按经过的小时和分钟移动，预览每个端点的新旧日期。已完成阶段和已结束的等待阶段保留历史日期，日期待定的端点继续待定；事项截止时间可选择是否一起移动。

仅移动天数时保留原日期精度。纯日期和全天安排按小时或分钟移动前，须明确原来的时刻，界面不会默认为午夜；全天安排补齐时刻后转为具体时段。跨夜自动展示新的日期。应用到草稿后须保存才生效，草稿和保存后的改期均可撤销。撤销仅恢复本次移动且之后未再改动的端点，保留后来新增的阶段、改名、提醒与完成记录。月重复日号随原重复基准一起恢复；之后单独修改过基准或日号时，保留后来设置，领域写入也不会重新计算并覆盖它。

具体时刻必须能在当前应用时区往返转换。夏令时跳过的时刻会定位提示；手动填写的截止时刻和日期提醒的独立时刻也按对应日期校验。按小时移动到重复小时而无法用现有日期与时刻精确表达时，拒绝该次改期并引导调整时长。

没有阶段的重复待办沿用原规则。有阶段的重复事项需要明确重复基准，默认推荐正式开始，其次使用截止日。所有阶段按相对基准的日历日偏移生成下一期，保留本地时刻，清除阶段完成时间及提醒消费记录。每月重复沿用月末夹取规则，并以原始锚点计算下一期基准。

重复生成同步移动所有阶段，重新分配阶段及提醒标识并重置完成记录。中间阶段完成保留后续安排，只有事项整体完成才生成下一期；最后阶段使用“完成事项”明确合并两项操作。下一期包含不存在的时刻时保留本期完成事实，显示未生成的原因，修改后保存可以重试。主动设置重复结束日期而不再生成下一期时，清除旧生成错误；延长结束日期后可以继续重试。撤销整体完成会恢复原阶段事实和生成错误状态，未被编辑的下一期也会一并撤回。

项目同步来的事项目前主要映射截止日和总体状态。第一版可以让项目事项继续使用现有项目时间能力；若允许编辑本地阶段，界面必须明确其只在个人事项范围同步，并且项目拉取保持这些字段。共享阶段功能需要单独设计项目端模型。

CSV 导入继续接受现有单截止格式。新增阶段需要定义明确列映射或 JSON 导入方式。支持带阶段事项的导出时保留完整阶段；格式容量不足时明确提示，避免静默丢失。

## 10. 实施范围与验收

首轮以现有个人待办为范围，一起完成自定义阶段编辑、阶段完成、摘要和下一步排序、首页与日历、提醒、冲突、重复兼容以及备份往返。主要流程使用通用名称和按需展开；常用组合模板可以后续增加。共享项目阶段、复杂依赖及服务端推送独立规划。

验收应使用虚构数据覆盖：

1. 只有截止时间的旧待办：展示、逾期、提醒和重复与原来一致。
2. 预约和正式安排共四个端点：逐阶段展示，并分别提醒。
3. 预约已办理：关闭前提醒停止，正式安排继续提醒，总事项仍未完成。
4. 窗口已关闭且未确认：风险区显示待确认，未来安排仍可见。
5. 正式安排已经结束：不自动勾选事项完成。
6. 只有正式安排、没有截止日：归入已安排，列表、首页、日历均可找到。
7. 只填一个端点、只填日期或日期均待定：保存已知信息，提醒与占用检查符合精度。
8. 跨午夜及跨月：结束日期、日历区间和重叠计算一致。
9. 窗口与其他安排重叠：按可办理时段展示；两段占用安排重叠：产生真实冲突提示。
10. 阶段改名、重排、改期、删除及撤销：标识稳定，提醒重算和去重正确。
11. 总体完成、取消、归档及撤销完成：阶段通知和风险展示正确。
12. 开放和关闭提醒在应用再次打开时补响：已关闭的窗口过滤过时通知。
13. 周期及月末重复：所有阶段进入下一期，完成情况重置，无旧日期残留。
14. 保存、刷新、备份恢复及账号同步：阶段与完成情况保留，日历派生条目可以回到源事项。
15. 手机与键盘操作：新增多个阶段后表单可滚动、无横向溢出，错误与操作具有明确标签。

方案的完成标准是一个事项能够表达多个自定义阶段的起止时间，用户快速录入、直接看到下一步，并且各页面、提醒和状态使用相同的时间含义。
